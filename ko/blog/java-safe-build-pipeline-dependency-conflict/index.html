외부 라이브러리 의존성 충돌 없이 안전한 Java 빌드 파이프라인 구축하기

SILENCE
2026년 10월 14일

대규모 엔터프라이즈 애플리케이션이나 마인크래프트 Fabric/Forge 모드를 개발할 때 가장 빈번하게 발생하는 런타임 악몽은 **'Jar Hell'**이라 불리는 라이브러리 버전 충돌 문제입니다. 내 모드가 사용하는 Guava v32와 다른 모드가 사용하는 Guava v21이 동일한 JVM 클래스로더에 로드될 때, 둘 중 하나는 반드시 NoSuchMethodError를 뿜으며 크래시를 유발합니다.

본 가이드에서는 Hera Klass와 Silence 생태계의 프로젝트들을 안전하게 배포하기 위해 구축한 Gradle Shadow 패키지 재배치(Relocation) 기법과 다이아몬드 의존성(Diamond Dependency) 해결 전략을 공유합니다.

1. Jar Hell 현상이 발생하는 구조적 이유

JVM은 기본적으로 'Flat Classpath' 모델을 사용합니다. 클래스로더는 클래스패스 목록의 앞에서부터 찾고자 하는 클래스명을 검색하고, 최초로 발견된 .class 파일을 즉시 메모리에 적재합니다.

[ 클래스패스 로딩 순서 ]
1. 타사 모드 A의 구형 ASM 라이브러리 (v7.0)  <-- 먼저 적재됨!
2. 내 모드 B의 최신 ASM 라이브러리 (v9.6)    <-- 무시됨!
==> 내 모드가 ASM v9.6의 신규 메서드를 호출하는 순간 java.lang.NoSuchMethodError 발생!

이 문제는 컴파일 시점에는 아무런 경고도 뜨지 않다가, 실제 사용자 환경에서 런타임에 불특정 모드와 결합할 때 돌발 크래시로 이어집니다.

2. 해결책: Gradle Shadow를 통한 패키지 재배치 (Package Relocation)

가장 확실하고 표준적인 해결책은 내 모드가 사용하는 외부 라이브러리를 단일 JAR에 포함(Fat Jar)시키면서, 패키지 네임스페이스를 완전히 격리된 고유 경로로 재배치(Relocate)하는 것입니다.

build.gradle 설정 예제

plugins {
    id 'com.github.johnrengelman.shadow' version '8.1.1'
}

dependencies {
    implementation 'org.ow2.asm:asm:9.6'
    implementation 'org.ow2.asm:asm-tree:9.6'
    implementation 'com.google.code.gson:gson:2.10.1'
}

shadowJar {
    archiveClassifier.set('')

    // 외부 라이브러리 패키지를 내 모드 고유 네임스페이스 하위로 강제 치환
    relocate 'org.objectweb.asm', 'net.silence.shadow.asm'
    relocate 'com.google.gson', 'net.silence.shadow.gson'

    // 불필요한 메타데이터 파일 소거로 JAR 용량 절감
    exclude 'META-INF/maven/**'
    exclude 'META-INF/LICENSE*'
}

이 설정이 적용되면 컴파일된 바이트코드 내의 모든 import org.objectweb.asm.ClassReader; 구문이 자동으로 import net.silence.shadow.asm.ClassReader;로 리네이밍됩니다. 다른 모드가 아무리 구버전 ASM을 로드하고 있더라도 내 모드는 완전히 격리된 자신만의 클래스를 참조하므로 충돌이 100% 방지됩니다.

3. 의존성 격리 3대 필수 원칙

  1. 절대 원본 패키지명을 Fat Jar에 그대로 넣지 말 것: Relocation 없이 라이브러리를 번들링하면 다른 모드의 클래스로더를 오염시켜 생태계 전체의 불안정성을 초래합니다.
  2. 리플렉션 문자열 주의: Class.forName("org.objectweb.asm.ClassWriter")처럼 하드코딩된 문자열은 Shadow 플러그인이 자동으로 리로케이션하지 못할 수 있으므로, 클래스 리터럴(ClassWriter.class.getName())을 사용해야 합니다.
  3. 불필요한 전이 의존성(Transitive Dependencies) 배제: implementation('...') { exclude group: '...' } 구문으로 필수적이지 않은 전이 의존성을 사전에 가지치기하세요.

Hera Klass는 이러한 패키지 재배치가 완료된 라이브러리 클래스까지 정밀 분석하여, 난독화 과정에서도 고유 패키지 경로를 보존하면서 완벽한 호환성을 보장합니다.
